## 2. A1 재판정 — 평문 열람을 만든다

`PLAN_ADMIN_FULL_CONTROL.md §2` 는 「평문 열람 기능은 만들지 않는다. 만들 수 없다」로 닫았다.
발주자가 그 판정을 뒤집었으므로 **이번 범위에 넣는다.** 다만 무엇이 가능하고 무엇이 불가능한지는 그대로다.

### 2-1. 가능한 것과 불가능한 것

- **과거 비밀번호는 복원 불가.** Supabase Auth 는 해시만 갖고 있고 평문을 돌려주는 Admin API 가 없다.
  이 기능을 켠 시점 **이후** 앱을 지나는 값부터 열람 대상이 된다.
- 비밀번호가 만들어지거나 바뀌는 경로는 **앱 내부 6개 + 앱 미경유 4개**다.
  앱 내부는 서버 세 지점이면 전부 잡힌다: `index.ts:173`(SME 생성 — 개별·일괄 공용),
  `index.ts:464`(`set-password` 합류점 — 서버 생성값·관리자 지정값 두 갈래), `index.ts:806` 직전(관리자 생성).
  **클라이언트는 손댈 필요가 없다.**
- 문제는 **본인 변경(P6)** 이다. `ChangePasswordPage.tsx:71` 의 `supabase.auth.updateUser` 만 브라우저가
  GoTrue 로 직접 쏘아 서버를 지나지 않는다. 그리고 신규 계정은 `must_change_password` 가 DEFAULT true 라
  `App.tsx:422` 가 첫 로그인에서 이 화면만 렌더한다 — **관리자가 발급한 값은 원래대로면 첫 로그인 직후 폐기된다.**
- 앱 미경유 4개(재설정 메일 / 대시보드·service_role / SQL 로 `encrypted_password` 직접 UPDATE / anon 키 signup)는
  앱 코드로 막을 수 없다. `auth.users` 에 걸린 트리거나 Auth Hook 이 현재 0건이다.

따라서 열람 화면이 약속할 수 있는 것은 「항상 정확한 값」이 아니라
**「앱을 통해 마지막으로 설정된 값 + 그 시각 + 이후 앱 미경유 변경 가능성 표시」**다.

### 2-2. 설계 3안

| 안 | 방식 | 열람 범위 | 공수 |
|---|---|---|---|
| **A. 전면 포착형** | 앱이 지나는 모든 설정값을 AES-GCM 으로 암호화해 전용 표에 적재. 본인 변경도 Edge Function 경유로 바꿔 포착 | 앱 경유 전량 | M(본인 변경 서버화까지 하면 +L) |
| **B. 관리자 전담형** | SME 의 자기 변경 자체를 없앤다(강제 변경 해제 + 변경 화면 제거). 관리자가 정한 값만 존재하므로 그것이 곧 실제 비밀번호 | 관리자 발급값 = 실제 값 | M |
| **C. 규칙 파생형** | 저장하지 않는다. 사번 기반 결정론적 규칙(`{empno}`·`{empno_last4}`·`{random4}`)으로 초기값을 만들고 화면이 다시 계산해 보여 준다 | 초기값만, 본인 변경 시 「변경됨」 표기 | L |

C 안의 원본은 `job-analysis-seoyon/src/lib/password-rule.ts` 다. **저장이 0** 이라는 점이 가장 안전하지만,
`profiles` 에 생년월일이 없어 토큰이 3종으로 줄고, 본인이 바꾼 뒤에는 값을 못 준다.

### 2-3. 채택 — A + B의 정책, C는 옵션

**A안을 채택하되, 파일럿 기간에는 B안의 정책을 함께 건다.**

- 보관: 신규 표 `public.account_password_vault`
  (`profile_id` PK / `ciphertext` / `key_version` / `source` / `stale` / `set_by` / `set_at`).
  `profiles` 에 컬럼을 붙이지 않는다 — `App.tsx:259` 가 `select('*')` 로 전 사용자 프로필을 매 로그인 읽고,
  `profiles!inner` embed 가 사방에 있어 그 순간 평문이 브라우저로 흘러간다.
- 암복호: **AES-256-GCM, Deno Web Crypto.** 키는 Edge Function 시크릿에 둔다(DB 밖).
  확장을 하나도 늘리지 않고, public 스키마에 평문을 뱉는 `SECURITY DEFINER` 함수를 만들지 않는다.
  pgsodium(공급사 폐기 예고)·Vault(래퍼 RPC 필요)·pgcrypto `pgp_sym`(키가 SQL 인자로 로그에 남는다)은 쓰지 않는다.
  선례가 이미 있다 — `RESEND_API_KEY` 를 같은 방식으로 다룬다(`send-reminder/index.ts:23,183`).
- 권한: **RLS 정책을 하나도 만들지 않는다.** 정책 없음 = 거부이고 `service_role` 만 통과한다 — `audit_logs` 와 같은 방식.
  더해서 `REVOKE INSERT,UPDATE,DELETE,TRUNCATE,SELECT ... FROM anon, authenticated` 를 같은 마이그레이션에 넣는다.
- 열람: Edge Function 신규 모드 `reveal-password` 하나. 대상 1건씩만. 목록 일괄 열람은 만들지 않는다.
  기존 관리자 검증(JWT → `auth.getUser` → `profiles.role='admin' AND active`, `index.ts:118-147`)이 모드 분기보다
  앞에 있어 새 모드가 그대로 상속한다. 화면에서는 **본인 비밀번호 재입력(재인증)** 을 요구하고,
  값은 마스킹 상태로 두었다가 눌렀을 때만 15초간 보여 준다.
- 감사: 열람 1건 = `PASSWORD_VIEWED` 1행. **`meta` 에는 `profile_id` 만 넣는다** — 값도 이메일도 넣지 않는다.
  `edgeApi.ts:153` 이 요청 body 를 그대로 들고 있으므로 `meta: body` 금지를 테스트로 고정한다.
- 정확도: `stale` 플래그. 앱 미경유로 값이 바뀌면 열람 화면이 값 대신 「앱을 지나지 않은 변경이 있었습니다」를 띄운다.
- 파일럿 정책(B): 관리자 발급 시 `must_change_password` 를 기본 **끔**으로 두고 SME 자기 변경을 열지 않는다.
  이 조건에서는 저장값 = 실제 비밀번호가 유지된다. 이 정책을 되돌리는 순간 저장값은 「발급값」일 뿐이다.

### 2-5. 남는 위험과 그 크기

이 설계가 막지 못하는 것은 **관리자 계정 탈취 한 가지**이고, 그건 요구된 기능 자체라 어떤 저장 수단으로도 못 막는다.
줄이는 방법은 열람을 공짜로 두지 않는 것뿐이다 — 재인증 + 감사 1행 + 관리자 계정 최소 유지.
백업·덤프 유출과 `service_role` 키 유출은 **키가 DB 밖에 있다는 것 하나로** 막힌다. 그래서 평문 컬럼을 쓰지 않는다.

### 3-2. 반복해서 나온 원칙 8가지

이 저장소에 그대로 적용되는 것만 골랐다.

1. **거짓 신호를 만들지 마라.** 미반영 설정을 반영된 것처럼 보이는 배지·문구로 표시하지 않는다.
   (job-analysis 커밋 `8246ced` 「거짓 신호 정리 — 미반영 설정 배지」)
2. **조회 실패를 「0건」으로 감추지 마라.** (`3b54fe2` 「조회 실패를 '아직 없습니다'로 감추지 않는다」)
3. **완료 주장은 타입체크·빌드가 아니라 실제 렌더된 화면 증거로.**
4. **"완료"는 원격에 반영된 시점이다.** 로컬 커밋만 하고 완료라 하지 마라.
5. **막다른 골목을 만들지 마라.** 모든 오류·빈 상태에 다음 행동을 준다. (`2868cbc` 「막다른 골목 해소」)
6. **반려·재작성 요청은 첫 화면에서 사유와 함께.**
7. **사람이 확인하지 않는 자동화는 편의가 아니라 위험이다.**
8. **비밀번호를 평문으로 로그·CSV 에 흘리지 마라 — 필요하면 옵션으로 명시 노출하라.**
   (`4147fbf` 「비밀번호 평문 기록 중단, CSV 비번 열 옵션화」)

원칙 8이 이번 §2 와 정면으로 만난다. 그때의 결론은 **「값을 흘리지 마라」가 아니라 「흘릴 자리를 정하고 그 자리만 열어라」**였다.
§2 의 설계가 같은 태도다 — 전용 표·전용 모드·재인증·감사 1행.
