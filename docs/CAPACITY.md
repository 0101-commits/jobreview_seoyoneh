# 동시접속 — 몇 명까지 되나 (2026-09-04)

**요구: 최소 50명 동시접속.**

## 0. 이 문서의 확인 수준

- 아래 숫자 중 **Supabase 쪽 한도는 공식 문서에서 확인**했다(2026-09-04 기준, 출처 표기).
- **부하 시험은 하지 않았다.** 이 저장소에는 부하 도구가 없고 파일럿 인원이 2~3명이라 재현할 수 없다
  (`docs/PILOT.md` §8-1 이 같은 사실을 이미 적어 두었다). 아래 계산은 **코드에서 읽은 요청 빈도**와
  **문서화된 한도**를 맞춘 것이지 실측이 아니다.
- 그래서 결론은 "된다"가 아니라 **"어디서 먼저 막히는지와 그 지점을 어떻게 비켜 갔는지"**다.

## 1. 결론

| 층 | 50명 동시 | 근거 |
|---|---|---|
| 정적 파일(GitHub Pages) | **여유** | CDN 정적 배포. 동시 접속과 무관하다 |
| 로그인 — 지속 | **여유** | `/auth/v1/token` IP당 **시간당 1800회**. 50명이 한 시간 안에 로그인해도 50회다 |
| 로그인 — **동시 폭주** | **여기가 먼저 막힌다** | 같은 엔드포인트의 **버스트 한도 30회**. 사무실 NAT 뒤 50명이 같은 1~2분에 몰리면 일부가 429 |
| 응답 저장(PostgREST → RPC) | **조건부 여유** | 아래 2절 계산. 요금제와 인스턴스 크기에 달렸다 |
| 비밀번호 재설정 메일 | **막힌다** | 내장 메일은 **프로젝트 전체 시간당 2통**. 애초에 파일럿 계정은 `.local` 이라 메일이 닿지 않는다 |

**즉 50명 동시접속 자체는 무리가 아니다. 위험은 「50명이 같은 순간에 로그인 버튼을 누르는 것」과
「요금제가 Free 인 채로 개시하는 것」 둘이다.**

## 2. 저장 부하 계산 — 사람 수 × 빈도

응답자 화면에서 서버로 나가는 요청은 **자동 저장 하나뿐**이다. 화면 안의 다른 타이머 둘은
네트워크를 쓰지 않는다(유휴 감지 5초 `src/App.tsx:235`, 저장 시각 표시 갱신 30초
`src/pages/sme-review/wizard.tsx:215`). 폴링·구독·Realtime 은 쓰지 않는다.

자동 저장은 **입력이 멈춘 뒤**에 한 번 나가고, 저장이 도는 동안에는 새 저장이 잡히지 않는다
(`savingRef` 가드). 그래서 한 사람의 최대 빈도는 `1 / 대기시간` 이다.

| | 대기 | 1인 최대 | 50명 최대 |
|---|---|---|---|
| 이번 변경 전 | 2.5초 | 24회/분 | **20회/초** |
| 이번 변경 후 | 6~8초(흔들림 포함) | 8회/분 | **7회/초** |

한 번의 저장은 `save_review_draft` RPC 하나이고, 그 안에서 다섯 표의 그 검토 행을 지우고 다시 넣는다
(`job_feedback`·`task_feedback`·`skill_feedback`·`new_task_suggestions`·`new_skill_suggestions` +
FTE 배분). 과업 30개·Skill 20개짜리 직무라면 저장 한 번에 50행 안팎이 오간다.

- 변경 전: 20회/초 × 50행 = **초당 1,000행 쓰기**
- 변경 후: 7회/초 × 50행 = **초당 350행 쓰기**

Postgres 로서는 둘 다 큰 수가 아니다. 문제는 **Free 요금제의 공유 인스턴스**(메모리 0.5GB, CPU 공유)와
커넥션 한도다. Pro 이상에서는 여유가 크고, Free 에서는 개시 직후 몇 분이 위태롭다.

> 실제 한도는 프로젝트마다 다르다. 개시 전에 **Supabase 대시보드 → Settings → Compute and Disk** 에서
> 요금제·인스턴스 크기를 확인하고, `docs/PILOT.md` §8-3 의 관측 항목을 개시 당일에 캡처한다.

## 3. 이번에 바꾼 것

| 무엇 | 어디 | 효과 |
|---|---|---|
| 자동 저장 대기 2.5초 → **6초 + 최대 2초 흔들림** | `src/pages/SmeReviewPage.tsx` | 최대 쓰기 빈도 1/3 이하. 흔들림은 같은 순간에 시작한 사람들이 같은 순간에 저장하는 것을 흩는다 |
| 혼잡 실패에만 **재시도 3회(0.8s → 1.6s, 흔들림 포함)** | `src/lib/reviewApi.ts` `saveReviewDraft` | 개시 직후의 일시적 429·503·타임아웃이 화면의 「저장하지 못했어요」로 바뀌지 않는다. 그 문구를 보면 사용자는 버튼을 연타하고, 그건 혼잡할 때 부하를 더 얹는 반대 행동이다 |

권한 오류(401·403)나 검증 오류는 재시도하지 않는다 — 다시 보내도 같은 답이 온다.

**입력이 더 위험해지지는 않는다.** 단계 이동·제출 전에 `waitForSave` 가 진행 중인 저장을 기다리고,
`beforeunload` 가 저장 안 된 상태로 나가는 것을 막는다. 늦어지는 것은 「저장됨」 표시뿐이다.

## 4. 개시 전에 해야 하는 것 (코드로는 못 막는 것)

1. **동시 로그인을 흩는다.** 이것이 가장 현실적인 실패 지점이다. 초대 메일을 전원에게 같은 분에
   보내지 말고 **조직·직군 단위로 나눠 발송**한다(15~30분 간격이면 충분하다).
   `/auth/v1/token` 의 버스트 한도가 IP당 30회이고, 사무실은 대개 NAT 하나를 공유한다.
2. **요금제를 확인한다.** Free 인 채로 50명 개시는 권하지 않는다.
3. **개시 당일 30분간 대시보드를 본다.** `docs/PILOT.md` §8-3 의 항목 그대로.
4. **비밀번호 재설정 메일에 기대지 않는다.** 내장 메일은 프로젝트 전체 시간당 2통이고,
   파일럿 로그인 ID 는 `.local` 이라 애초에 닿지 않는다. 못 들어오는 사람은
   관리자 화면의 **임시 비밀번호 재발급**으로 처리한다(그 경로는 메일을 쓰지 않는다).

## 5. 아직 모르는 것

- **실측이 없다.** 위 수치는 전부 코드에서 읽은 빈도와 문서화된 한도의 곱이다.
  1회차 개시 때 실제 값을 재서 이 문서에 붙여야 한다.
- **동시 편집 충돌은 별개 문제다.** 낙관적 락이 없어서, 같은 사람이 두 탭을 열면 나중 탭의
  자동 저장이 앞 탭 입력을 덮는다(`docs/PLAN_2026-09-04_IMPROVEMENT.md` P1-19).
  사람 수가 아니라 **탭 수**의 문제라 이 문서의 계산과는 다른 축이다.
- **1000행 절단**이 남은 관리자 조회 3곳은 응답자 수가 늘수록 먼저 드러난다(같은 기획서 P1-20).
  직무 40 × SME 25 = 1,000 을 넘는 순간 「N명 중 M명 제출」의 분모가 조용히 줄어든다.
